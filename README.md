# factorizer

Параллельный факторизатор целых чисел с графическим интерфейсом на Qt Quick.
Числа до 512 бит раскладываются квадратичным решетом (2LP-SIQS), более
крупные — методами Полларда и ECM.

# Возможности

* **2LP-SIQS** (`siqs_xor.hpp`) — самодостаточное квадратичное решето с
  большими простыми: один проход по A-полиномам, байтовые логарифмы в
  L1/L2-сите, hit-map больших простых, лес 2LP-циклов и разреженный гаусс
  над GF(2) с XOR-историей строк.
* **Арифметика фиксированной ширины** (`bignum.hpp`): `UInt<Bits>` с
  64-битными лимбами, деление по Кнуту, Барретт-редукция, `U128…U4096`.
* **ECM** (две стадии) и методы Полларда (p−1, Брент-ро). ECM-лестница
  включается только там, где решето неприменимо — для чисел крупнее 320 бит;
  авторежим запускает решето до 320 бит.
* **Потоки** — `std::thread` с привязкой к P-ядрам (`cpu_topology.hpp`).
* **Прогресс** — сквозной канал из решета в интерфейс: полоса и проценты,
  значение монотонное (см. `FactorizerBackend::setProgress`).
* Генератор полупростых чисел p×q, тёмная/светлая тема, выбор метода
  (авто / принудительный SIQS).

# Сборка

Qt 6.11, CMake, Ninja и llvm-mingw (clang):


# Производительность

Стенд: Intel Core i7-8565U (4 ядра / 8 потоков), 16 ГБ ОЗУ, Windows 11,
Qt 6.11.1, clang 17 (llvm-mingw), сборка Release (`-O3`).

Методика: числа — полупростые p×q, сгенерированные встроенным
`generate_semiprime` (seed = 1000 + битность), факторизация — через
`factor_parallel_generic` в режиме «Авто». Время — от запуска конвейера до готового
разложения, без учёта генерации числа; память — пиковый рабочий набор
процесса (`PeakWorkingSetSize`).

| Битность | Время | Пиковая память |
|---:|---:|---:|
| 100 | 1.36 с | 42 МБ |
| 128 | 0.44 с | 16 МБ |
| 160 | 0.61 с | 18 МБ |
| 192 | 1.45 с | 26 МБ |
| 224 | 9.6 с | 54 МБ |
| 256 | 70 с | 114 МБ |
| 272 | 257 с | 195 МБ |
| 300 | 1523 с | 425 МБ |

Каждый размер мерялся отдельным процессом (иначе пик памяти складывается с
предыдущими числами серии).

Разброс между прогонами на ноутбуке — до ±20–30 % (троттлинг), поэтому
сравнивать имеет смысл только парные замеры в одной сессии. Строка 300 бит —
именно такой парный замер: до оптимизаций 1780 с, после 1523 с (−14.4 %).

Воспроизведение (сборка бенчмарка — в разделе «Тесты»):

```powershell
tests\bench_semiprime.exe 100 128 160 192 224 256 272 300
```

Замечания:

* до ~200 бит разложение занимает секунды; после 256 бит время растёт круто
  (в 4–5 раз на каждые 16 бит), а память — пропорционально размеру
  матрицы Гаусса;
* авторежим запускает решето до 320 бит; выше — только ECM и методы
  Полларда;
* на малых размерах время не монотонно: для 100-битного числа решето с
  запасом перебирает соотношения (порция полиномов удваивается), и матрица
  получается крупнее, чем у 128-битного (отсюда 1.45 с против 0.40 с);
* граница факторной базы в `auto_tune_siqs` снижена примерно втрое
  (свободный член формулы 3.3 → 2.0): полиномов становится больше, но
  каждый дешевле, а матрица Гаусса меньше. Парные замеры полного конвейера
  «до → после»: 0.99 → 0.61 с (160 бит), 2.53 → 1.42 с (192),
  22.1 → 10.0 с (224), 142 → 89 с (256), 389 → 307 с (272);
  на 300 битах время почти не изменилось (1880 → 1834 с), зато память
  упала с 1.9 ГБ до 425 МБ — там узкое место уже не база, а размер матрицы;
* `block_bits` = 17 включается с 150 бит (раньше с 200): на 160/192 битах
  более широкий блок дешевле просева, а на 128 — наоборот, поэтому там
  остаётся 16;
* если факторная база упирается в нижний предел 50 000 (числа до ~182 бит),
  число множителей `s` уменьшается на единицу: годных `q` меньше, чем
  предсказывает формула, и лишний множитель в `A` портит полиномы
  (на 160 битах: 0.62 → 0.40 с);
* скан блока на выживших кандидатов векторизован (SSE2, 16 байт за такт):
  это самая дорогая фаза после просева, ускорение самой фазы ~10×;
* сбор крупных простых больше не ходит в хеш-таблицу: выжившие позиции лежат
  в компактном списке, а проверка «корень попал в выжившую позицию» — это один
  бит из карты на 16 КБ, целиком помещающейся в L1. На 256 битах это
  89 → 68 с, на 272 — 307 → 302 с. Позиция при этом едет вместе с индексом
  простого в одном `u64`, поэтому второй проход идёт по плотному массиву и не
  перечитывает `sol1/sol2` по случайным адресам;
* пересчёт корней `sol1/sol2` при смене полинома векторизован (SSE2, четыре
  простых за такт), а ветка «простое выбрано в `A`» убрана: у таких простых
  дельта равна нулю, поэтому сдвиг и так нулевой. На 300 битах это 12 %
  времени, и обновление идёт по 42 тыс. простых на каждый полином;
* подготовка `A` ускорена пропуском незначащих старших слов в `divrem_u64`
  (`bignum.hpp`): числа в решете — это 3–6 слов из 8, а на каждое простое базы
  приходится 11 делений. На 300 битах подготовка `A` — 141 мс на набор и 12 %
  времени;
* пробное деление больше не считает `s_idx % p` аппаратным делением: остаток
  восстанавливается из предвычисленного `floor(2^32 / p)`;
* множители выжившего кандидата собираются в переиспользуемый буфер, а не в
  новый `vector` на каждого кандидата (на 256 битах это было ~400 тыс.
  аллокаций за проход);
* ECM-лестница перед решетом больше не запускается: на 205-битном
  полупростом она тратила 85.1 с (0.07 + 0.60 + 11.3 + 73.1 по тирам) и
  делитель не находила, тогда как решето укладывалось в 12.0 с — итог был
  97.6 с против 10.6 с. Теперь ECM работает только там, где решето
  неприменимо (крупнее 320 бит), и ничему не мешает;
* принудительный SIQS снимает ограничение 320 бит, но выше 512 бит метод
  неприменим (жёсткий предел реализации).

Последний раунд правок (SSE2-обновление корней, деление без незначащих старших
слов, `floor(2^32 / p)` в пробном делении, буфер множителей) на 300 битах даёт
1780 → 1523 с (−14.4 %) при той же памяти 425 МБ. Основной вклад — корни и
подготовка `A`: на этой размерности они занимают по 12 % времени каждая.

## Почему после 272 бит время растёт так круто

Это не ступенька в коде, а сложный процент: примерно +7 % на бит
(224 → 256 — 7.3×, 256 → 272 — 3.7×, 272 → 300 — 5.9×; разброс по шагам —
следствие троттлинга ноутбука). Внутри шага
272 → 300 бит умножаются три вещи:

* **соотношений нужно больше** — база растёт с 550 тыс. до 1.08 млн, простых
  в ней с 22.7 до 42.1 тыс., и матрица Гаусса становится вдвое шире (×1.85);
* **выход с полинома падает** — |Q(x)| ≈ 2^(bits/2 + block_bits) вырастает на
  14 бит, а база — всего на 1 бит, поэтому гладких значений на кандидата
  становится в 2.75 раза меньше (0.026 → 0.0077 соотношения на полином);
* **полином дорожает** на 20–30 % — фазы, пропорциональные числу простых
  (корни, подготовка A, пробное деление), растут вместе с базой, а сам просев
  почти нет: его цена ~ B·Σ1/p, а Σ1/p растёт как ln ln p.

Профиль 300 бит (5.46 млн полиномов, 10 728 наборов A): просев 73 %,
пересчёт корней 12 %, подготовка A 12 %, разложение 1.3 %, сбор крупных
простых 1 %, скан 0.5 %, гаусс 2 % (37 с на матрице 27 039 × 26 629).
Для сравнения, на 256 битах просев — 63 %, а сбор крупных простых — 15 %.

## Что ещё проверено и отвергнуто на 300 битах

Опорное значение в сравнениях ниже — 1508 с (одиночный стенд, одна сессия);
в таблице выше стоит парный замер 1523 с.

* **ширина блока 19** — 1877 с против 1508 с: блок 512 КБ уже не помещается
  в L2 (256 КБ на ядро), просев уходит в L3. 18 — оптимум;
* **потолок `s` = 11** — 1546 с против 1508 с: выигрыш от вдвое более редкой
  подготовки A не покрывает ухудшения полиномов (множители `A` становятся
  мельче при том же размере `A`);
* **рост базы на 272 битах** (550 тыс. → 1.1 млн → 2.2 млн): 303 → 300 → 350 с,
  то есть оптимум по базе уже достигнут.

# Тесты

Исполняемые файлы собираются вручную из корня проекта (Qt не требуется —
нужен только компилятор и `-pthread`):

```powershell
clang++ -std=c++20 -O3 -DNDEBUG -pthread -I. tests/test_bignum.cpp    -o tests/test_bignum.exe
clang++ -std=c++20 -O3 -DNDEBUG -pthread -I. tests/test_siqs_xor.cpp  -o tests/test_siqs_xor.exe
clang++ -std=c++20 -O3 -DNDEBUG -pthread -I. tests/test_pipeline.cpp  -o tests/test_pipeline.exe
```

Бенчмарк (время и пиковая память; под Windows дополнительно `-lpsapi`):

```powershell
clang++ -std=c++20 -O3 -DNDEBUG -pthread -I. tests/bench_semiprime.cpp -o tests/bench_semiprime.exe -lpsapi
tests\bench_semiprime.exe 128 192 256            # сгенерировать полупростые и разложить
tests\bench_semiprime.exe --n 633825300158679507911716700309   # разложить заданное число
```

`tests/factorizer_siqs_etalon.py` — эталонная реализация решета на Python
(для сверки результатов), `tests/siqs_xor.cpp` — исходный прототип, с
которого портирован `siqs_xor.hpp`.

# Структура

| Файл | Назначение |
| --- | --- |
| `bignum.hpp` | `UInt<Bits>`, Барретт-редукция, модульные операции (`bignum::ops`) |
| `siqs_xor.hpp` | 2LP-SIQS: сито, циклы больших простых, гаусс над GF(2) |
| `generic_factorizer.hpp` | конвейер: пробное деление → Поллард → решето (ECM — крупнее 320 бит) |
| `u128_intrinsics.hpp` | переносимые 64-битные примитивы (carry/borrow/64×64) |
| `u128_utils.h` | глобальный флаг остановки, решето простых |
| `cpu_topology.hpp` | число рабочих потоков и привязка к P-ядрам |
| `factorizerbackend.*` | мост C++ ↔ QML: свойства, потоки, статус, прогресс |
| `Main.qml` | интерфейс |
| `tests/` | тесты, бенчмарк, эталонные реализации |
